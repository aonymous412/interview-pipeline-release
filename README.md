# Code and data release (anonymised for double-blind review)

Anonymised code and data release accompanying the paper *Knowing When to Stop Asking: A Formal
Coverage Criterion for Multi-Turn User Intent Understanding* (under double-blind review;
the authors are not identified anywhere in this repository).

It contains the pipeline implementation, the evaluation harness, the prompt set, the three
parameter spaces, the human annotations, and the raw per-run records behind every number in
the paper. The Reproducibility Artifacts and Baseline Interview Protocol appendices of the
paper describe these files and quote the four protocol prompts verbatim; the tables they
carry recompute from what is here. `DATA_ACCESS.md` states, dataset by dataset, what is here
and how to obtain what is not.

## Supplementary material

`supplement.pdf`, at the root of this repository, contains the appendices of the paper
(Appendices A to L). Its first page is an index that links each appendix to the files of this
repository it draws on, so that every table and figure in the appendices can be traced to a
record under `results/`, `data/` or `training/`, or to the script that produced it.

## Paper

`paper.pdf`, also at the root of this repository, is the anonymised PDF of the paper itself
(main text and references). It is the version under review; the appendices in `supplement.pdf`
and the layout of this repository follow its order.

## Start here: verify the paper's numbers in one command

```bash
pip install numpy
python verify_numbers.py
```

No API key, no model download, no re-run. `verify_numbers.py` imports only `numpy`; the
first four pinned lines of `requirements.txt` (numpy, scipy, pandas, scikit-learn) cover it
and every offline analysis script, and install in well under a minute. The remaining lines
(sentence-transformers, google-genai, anthropic) are needed only to re-run the pipeline
against the hosted models. Each record stores the resolved frame **and** the
per-turn coverage trajectory of its run, so every mean, bootstrap interval, turn count and
stopping statistic in the paper is recomputable offline. The script prints each recomputed
value next to the value claimed in the paper and exits non-zero on any mismatch.

It opens with an integrity pass that does not consult the paper at all: it recomputes
$\mathrm{cov}(F)$ for all 450 ALI runs from the stored frame and the published weight
vector, and checks it against the value the record carries — exactly, with no tolerance —
along with the trajectories, the stopping labels and the per-domain weight totals. That
establishes the coverage figures as arithmetic on the frames before any statistic over them
is compared to anything. `PROVENANCE.md` sets out the whole chain, which links of it are
verifiable from this archive and which are not.

## What this code is, and what it is not

This archive ships **the evaluation harness that produced the published numbers**, not a
reimplementation of it. Every value in the paper was computed by the files in `code/ali/` and
`code/phase1/` as they appear here, against the records in `results/`.

One consequence is stated in the paper's Setup and Protocol subsection and repeated here,
because it is the first thing a reader of `code/ali/components/c3_generator.py` will notice.
The evaluated harness instantiates **C3 with a single candidate question per turn**, drawn
from the highest-weight cluster. The reward-based ranking over six candidates from a
three-tier source, described in the Question Selection and Stopping Criterion subsection and
in the Question Selection appendix, belongs to the deployed systems: it does not run in this
harness, and no number in the paper depends on it.
The paired ablation reported in the paper suggests the difference matters little, but we have
not measured it directly. Faced with the choice, we ship the code that produced the results
rather than code that matches the architecture description.

The per-domain thresholds hard-coded in `code/ali/ali_pipeline.py` (Consulting 0.90, Medical
0.90, Payments 0.75) are the values the published runs used and are the values the paper
reports. The same holds for the bootstrap seed and resample count in `evaluate.py`.

The research repository stores each result file next to the script that wrote it; this
archive groups them into `code/`, `data/` and `results/` instead. Import statements and
directory constants were rewritten to match that layout, and nothing else was: no threshold,
seed, formula or published value differs from the code that produced the results. Rewritten
lines carry a `[relocated]` marker and `RELOCATION.txt` lists every one of them, generated by
the build from the rewrites it applied. `PROVENANCE.md` explains why.

## Layout

```
code/ali/            the five-component pipeline (C0-C4) and the evaluation harness
  ali_pipeline.py      orchestrator: the while cov(F) < theta_d loop
  components/          c0_detector, c1_identifier, c2_clusterer, c3_generator, c4_extractor
                       c3_generator: single-candidate C3, see the section above
  config.py            all paths, the per-deployment defaults, MAX_TURNS = 15
  coverage_scorer.py   the LLM-as-judge scorer validated at kappa = 0.749
  gemini_client.py     thin API wrapper (key read from the environment)
  taxonomy_mapping.py  maps each deployment's native fields onto the flat parameter space
  user_simulator.py    the oracle-simulated user shared by ALI and the baselines
  evaluate.py          bootstrap_ci: percentile bootstrap, B = 10,000, seed 42
  run_phase2.py        main evaluation entry point (ALI_v1 / v2 / v3)
  ablation.py, ablation_stats.py       paired ablation and its Wilcoxon/TOST analysis
  run_theta_sensitivity.py             the threshold sweep
  h1_sanity_check.py                   the descriptive control on hypothesis H1'
  per_domain_baselines.py              per-domain decomposition
  radassist_extraction_eval.py         the 50-report Medical extraction evaluation; needs
                                       MIMIC-CXR, which cannot ship (see DATA_ACCESS.md)
  cost_analysis.py, cost_instrumentation.py, run_cost_latency.py
code/phase1/         the baseline harnesses (single-pass, multi-turn) and the kappa computation
  run_multiturn.py     the interviewer and oracle system prompts shared by every baseline,
                       reproduced verbatim in the Reproducibility Artifacts appendix and
                       discussed in the Baseline Interview Protocol appendix
  run_multiturn_claude.py  the same protocol for the three frontier models
  run_exp2.py          the single-pass extraction baseline over the 150 prompts
  run_exp3.py          the scorer-validation run that produced the annotation sheet
  claude_judge.py      the cross-family second judge (Claude Sonnet 5)
  compute_kappa.py     Cohen's kappa, overall / by domain / by tier
  scoring.py           the scorer prompt and the RESOLVED/MENTIONED/ABSENT definitions
data/                the 150 prompts (P01-P50 and N01-N100), the three parameter spaces
                     with their importance weights, and the 516 human annotations
  prompts_qc.csv       per-prompt review sheet: measured columns filled, judgement
                       columns deliberately empty (the review pass is not done)
results/ali/         one record per ALI run, all configurations
results/baselines/   one record per baseline run, all six models
results/scoring/     scorer-validation statistics
training/            the two fine-tuned components of the FinAgent deployment
  c1/, c4/             adapter_config.json (the exact LoRA setup), training_history.json
                       (per-epoch train and eval loss), and the train/eval splits
                       -- the training table of the paper recomputes
                       from the two training_history.json and from nothing else
reports/             the analysis reports the appendices summarise
PROVENANCE.md        how each number is obtained, link by link, and what this
                     archive can and cannot establish
RELOCATION.txt       the path rewrites applied when the repo layout was regrouped
                     into this one, generated by the build
```

Scripts re-run from this archive write to a `recomputed/` directory rather than over
`results/` and `reports/`, so the shipped evidence stays as it was and a re-run can be
diffed against it.

Two notes on `training/`. Only **two** of the five components are fine-tuned: C3 generates
questions through the hosted model in every deployment and is never trained, so the training
table has two rows, not three. And the checkpoint the paper calls **C4** is named
`c3_param_extractor` in the implementation; the splits are renamed here to the paper's
numbering so that the directory reads as the paper does.

## Reproducing from scratch

Re-running the pipeline (rather than recomputing from the records) needs API access to the
hosted models and Ollama for the two local ones:

```bash
pip install numpy scipy pandas scikit-learn sentence-transformers google-genai anthropic
export GEMINI_API_KEY=...    # scorer, C4, and the Gemini baselines
export ANTHROPIC_API_KEY=... # the oracle user and the three Claude baselines
python code/ali/run_phase2.py --config ALI_v1     # writes to recomputed/
```

The offline analysis scripts need no key and run against the shipped records:

```bash
python code/ali/evaluate.py               # per-configuration means and bootstrap CIs
python code/ali/per_domain_baselines.py   # the per-domain decomposition
python code/ali/ablation_stats.py         # the paired ablation, Wilcoxon and TOST (needs scipy)
```

Expect a re-run not to reproduce a domain mean to the digit: the pipeline calls hosted models,
and re-executing an unchanged configuration two weeks apart moved a domain mean by 0.9 pp with
37 of 50 runs identical. The paper reports that figure so that differences of that size are not
read as effects. Everything that does **not** depend on a model call — coverage arithmetic,
bootstrap intervals, the ablation statistics, the truncation control — is deterministic under
seed 42 and reproduces exactly.

## What is not here, and why

- **The three production deployments.** This package contains the ALI pipeline and everything
  the paper measures. The surrounding product codebases (clinical front end, project-scoping
  service, financial enforcement engine) are out of scope and would not be reviewable.
- **Model weights.** The fine-tuned adapters (1.62 M to 18.46 M trainable parameters) come to
  91 MB and are omitted from this archive for size. What is here instead is everything needed
  to re-run the fine-tune: `training/` carries the exact LoRA configuration, the train/eval
  splits, and the per-epoch loss history that the training table of the paper
  is recomputed from. The evaluated configuration ALI_v1 falls back to a hosted model for C4
  in any case.
- **MIMIC-CXR reports.** Redistribution is prohibited by the data licence. `DATA_ACCESS.md`
  gives the access route.
- **The adversarial suite.** Its generators are not seeded and its totals therefore vary
  between runs, which the paper states; the paper makes no claim resting on it.
